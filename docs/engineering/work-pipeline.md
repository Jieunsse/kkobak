# 꼬박 작업 흐름 설계

2026-11-27에 정했다. 출발점은 크루런(이전에 만든 러닝 대회 앱 프로젝트, 레포 이름 bukang)의 `docs/decisions/`에 있는 맷 포콕 흐름 설계다. 맷 포콕 흐름은 맷 포콕 스킬(Matt Pocock이 만든 Claude 작업 스킬 묶음)로 일하는 방식이다. adflow(먼저 이 흐름을 혼자 개발용으로 고친 다른 프로젝트)가 이 설계를 `docs/engineering/matt-pocock-flow.md`로 고쳤고, 꼬박은 그 문서를 바탕으로 다시 고쳤다.
라벨, 브랜치, 제목, 영역, 양식은 [GitHub 규칙](github-conventions.md)에 따로 있다.

## adflow 설계와 달라진 점

| 부분 | adflow | 꼬박 | 이유 |
|---|---|---|---|
| 코드 | 이미 있음. lint 위반 기준선(지금 있는 위반을 허용해 두는 목록)이 있음 | 아직 없음 | 검사를 처음부터 엄격하게 켠다. 레칫(예외 목록을 하루 한 파일씩 줄이는 작업)은 두지 않는다 |
| 구독 | Claude Max 기준 | Claude Pro, ChatGPT Plus | 두 요금제 모두 한도가 작다. 그래서 GitHub Actions에서 Claude를 돌리는 자동 작업(4절 다크 팩토리)은 켜지 않는다 |
| 구현 | 기본은 Claude, 병렬일 때 Codex | 화면은 Claude, API와 로직은 Codex | 두 한도를 고르게 쓴다. 피그마를 읽어야 하는 일과 판단이 필요한 일만 Claude가 맡는다 |
| 리뷰 | Actions의 Claude 자동 리뷰 | 교차 리뷰. Codex가 만든 것은 Claude가, Claude가 만든 것은 Codex가 본다 | 같은 모델은 같은 실수를 놓친다 |
| 규칙 문서 | AGENTS.md | AGENTS.md가 원본이고, CLAUDE.md는 `@AGENTS.md` 한 줄 | Codex는 AGENTS.md를, Claude는 CLAUDE.md를 읽는다. 이렇게 두면 규칙을 한 곳에서만 고친다 |
| 브랜치 | dev와 main | main 하나 | 혼자이고 배포 환경이 하나다. 브랜치가 하나면 보호 규칙도 하나다 |
| 구조 점검 | 매주 금요일 | 운영을 시작한 주부터 매주 금요일 | 만드는 4주에는 점검할 코드가 적다 |

## 1. 메인 흐름

```
기획·정책 (docs/planning) + 가설 (docs/planning/hypotheses.md)
  → 기능마다 설계 세션 하나 (Claude): grill-with-docs → to-spec (스펙에 가설과 측정할 행동을 적는다)
  → to-tickets ①: API·로직 티켓 (「Codex 구현」). 시안을 기다리지 않는다
  → 화면 시안 (사용자, 피그마): 스펙의 사용자 흐름과 화면 목록을 보고 그린다
  → to-tickets ②: 화면 티켓 (「Claude 구현」, 피그마 프레임 링크)
  → 티켓마다 구현
      「Codex 구현」: Claude가 지시서 작성 → codex exec → Claude가 diff 읽기·테스트 실행·두 축 리뷰 → PR
      「Claude 구현」: 새 Claude 세션이 티켓과 피그마 프레임만 보고 구현 → PR → Codex 리뷰
  → 머지: CI 필수 체크 통과 + 「읽고 이해함」 체크박스를 직접 확인
  → 그 세션에서 retro
  → 사용자가 쓴다 → 판정 시점에 가설 판정 (맞음 / 틀림 / 보류) → 키우기·고치기·지우기
```

흐름에 나오는 이름의 뜻:

- `grill-with-docs`: Claude가 기획 문서와 용어집을 옆에 두고 설계를 질문으로 따져 묻는 스킬이다.
- `to-spec`: 정한 설계를 스펙 이슈(GitHub 부모 이슈)로 적는 스킬이다.
- `to-tickets`: 스펙을 구현 단위의 티켓(하위 이슈)으로 나누는 스킬이다.
- 두 축 리뷰: PR을 두 기준으로 보는 리뷰다. 스펙 축은 PR이 닫는 티켓, 그 부모 스펙 이슈, 명세의 절과 맞는지 본다. 기준 축은 [리뷰 기준](../../CODING_STANDARDS.md)의 항목을 지키는지 본다.
- retro: 작업을 마친 뒤 실수를 돌아보고 규칙에 반영하는 짧은 회고다. 어디에 반영하는지는 아래 표의 retro 항목에 있다.

화면 시안 원본: [꼬박 피그마](https://www.figma.com/design/gf5NAEGyhDA01o7P0LWoQt/%EA%BC%AC%EB%B0%95?node-id=0-1)

| 결정 | 왜 |
|---|---|
| 새 문서를 만들거나 문서 이름을 바꾸면 [문서 색인](../README.md)에 한 줄을 고친다. 문서는 색인 하나로 찾는다 (2026-11-27) | 문서가 늘어도 어디에 무엇이 있는지 한곳에서 본다 |
| 정책이 정해지거나 바뀌면 같은 작업 안에서 두 곳을 함께 고친다. 하나는 레포 `docs/planning/`의 원본 문서이고, 다른 하나는 피그마 「01 정책」 페이지의 요약 카드다(기획은 「00 기획」 페이지). 레포가 원본이고 피그마는 요약이다 (2026-11-27) | 시안을 그리는 사람이 피그마에서 최신 정책을 본다. 한쪽만 고치면 둘이 어긋난다 |
| 모든 기능은 가설에서 출발한다 (2026-11-27). 스펙 이슈에 [ 가설 ] 블록을 두고 가설, 측정(분자·분모·기간), 기준선(맞음·틀림을 가르는 숫자), 판정 시점을 적는다. 가설은 [기능 가설](../planning/hypotheses.md) 문서의 카드를 가리킨다 | 만든 기능이 실제로 문제를 푸는지 사용자의 행동으로 확인한다 |
| 측정에 필요한 사용자 행동 기록은 그 기능의 API·로직 티켓 안에 넣는다. 기록 없이 기능만 머지하지 않는다 | 기능을 다 만든 뒤에 측정을 붙이면 처음 몇 주의 기록이 비어 판정할 수 없다 |
| 스펙 이슈는 티켓이 모두 끝나도 닫지 않고 「검증 대기」 라벨을 붙여 둔다. 판정 시점에 판정 기록을 댓글로 남기고 「검증됨」 또는 「기각」 라벨을 붙여 닫는다 | 기능은 "다 만들어짐"이 아니라 "검증됨"에서 끝난다 |
| 판정은 미리 정한 기준선으로 한다. 기준선은 출시 전에 정하고 결과를 본 뒤에 바꾸지 않는다. 사용자가 100명 규모라 사용자를 둘로 나눠 비교하는 실험은 하지 않는다 | 숫자가 작아 비교 실험으로는 결론을 내기 어렵다. 결과를 보고 기준을 바꾸면 무엇이든 성공이 된다 |
| 월요일 아침에 이슈를 분류할 때 판정 시점이 지난 가설을 함께 본다 | 판정을 잊지 않는다 |
| 설계 세션 하나는 기능 하나를 다룬다. 설계 세션이 읽는 자료는 `docs/planning`에서 그 기능을 다룬 절과 [용어집](../../GLOSSARY.md)이다 | 스펙 축 리뷰가 PR을 명세의 한 절과 맞춰 보기 때문이다 |
| 화면 시안은 스펙이 정해진 뒤에 그린다 (2026-11-27). 스펙 이슈에 사용자 흐름, 화면 목록, 화면마다 보여 줄 상태(빈 상태, 오류, 마감 직전 등)를 적는다 | 정책과 흐름이 정해진 뒤에 그려야 시안을 다시 그리지 않는다. 시안을 그리다 스펙에 빠진 상태가 보이면 스펙을 고친다 |
| to-tickets는 두 번 나눠 돌린다. 스펙 직후에는 API·로직 티켓만 만들고, 시안이 나온 뒤에 화면 티켓을 만든다 | 서버 구현이 시안을 기다리지 않는다. 화면 티켓은 피그마 프레임 링크가 있어야 구현할 수 있다 |
| 스펙은 GitHub 부모 이슈, 티켓은 하위 이슈다. 먼저 끝나야 하는 티켓은 GitHub의 차단 관계(blocking) 연결로 표시한다 | 맷 포콕 스킬이 GitHub를 기본으로 지원한다 |
| 티켓마다 「Codex 구현」 또는 「Claude 구현」 라벨을 붙인다. 화면이 바뀌는 티켓은 「Claude 구현」이고 피그마 프레임 링크를 적는다 | Codex와 다크 팩토리(4절)의 러너는 피그마에 로그인할 수 없다 |
| API가 바뀌는 티켓은 스펙에 `contracts/`에서 바뀌는 부분을 적는다 | 서버와 앱이 같은 계약을 본다. 리뷰어가 계약과 구현이 맞는지 본다 |
| Codex에 넘길 때는 전역 규칙의 지시서 양식(`~/.claude/codex-instruction-template.md`)과 검증 기준을 그대로 쓴다. Codex가 끝냈다고 말해도 그것만으로 완료라고 하지 않는다. Claude가 테스트를 직접 돌린 뒤에 PR을 연다 | 사용자 전역 규칙과 같다 |
| 여러 티켓을 동시에 할 때는 Codex를 여러 개 돌린다. 같은 파일을 만지는 티켓은 동시에 돌리지 않는다 | 두 구현이 같은 파일을 덮어쓰지 않게 한다 |
| retro는 사람이 연 Claude 세션이 끝날 때 그 세션 안에서 한다. 기계로 잡을 수 있는 실수는 lint·CI 규칙에 더하고, 판단이 필요한 것은 [리뷰 기준](../../CODING_STANDARDS.md)에 더한다 | 구현자가 읽을 글을 늘리지 않는다 |

### 한 주 나누기

**만드는 4주 (2026-12 ~ 2027-01)**

| 언제 | 하는 일 |
|---|---|
| 월 아침 | 이번 주 티켓을 칸반의 「이번 주」 칸에 넣는다 |
| 매일 오전 | 사용자는 스펙이 나온 기능의 화면 시안을 그린다. Claude는 설계 세션을 하거나 Codex 지시서를 쓴다 |
| 매일 오후 | Codex 구현을 병렬로 돌리고, Claude는 화면 티켓을 구현한다 |
| 매일 마지막 | 리뷰, 머지, retro |
| 금 오후 | 한 주를 돌아본다. Claude와 Codex 사용량을 확인한다 |

| 주차 | 사용자 (시안) | 구현 |
|---|---|---|
| 1 | 로그인, 그룹 만들기, 초대 | 서버 기본 구조, 로그인과 그룹 API |
| 2 | 인증, 그룹 현황, 장부 | 1주차 화면, 인증·판정·장부 API |
| 3 | 정산표, 카드 공유 | 2주차 화면, 알림. 지인 테스트 시작 |
| 4 | 소개 페이지, 테스트 피드백 | 남은 화면, 소개 페이지, 출시 |

**운영 8주**

| 언제 | 하는 일 |
|---|---|
| 월 아침 | `/triage`(이슈를 읽고 라벨을 붙여 분류하는 스킬)로 사용자 피드백 이슈를 분류한다 |
| 월~목 | 지표를 보고 개선한다 (설계 → 구현) |
| 금 | 로컬에서 `improve-codebase-architecture`(코드 구조를 훑어 고칠 후보를 찾는 스킬)를 돌려 후보 하나를 고르고 리팩토링한다. 버릴 이유가 분명한 후보는 ADR(되돌리기 어려운 결정 기록)로 남긴다. 넓게 퍼지는 변경은 넓히기(새 방식 추가) → 옮기기(쓰는 곳 이전) → 줄이기(옛 방식 삭제)로 나눈다. 못 끝낸 티켓은 다음 금요일로 넘긴다 |

옛 테스트는 리팩토링 PR에서만 지울 수 있다. 새 인터페이스의 테스트가 같은 동작을 확인하고 통과한 뒤에 지운다. PR에는 지운 테스트와 그 자리를 대신하는 테스트를 짝지어 적는다.

### 한도가 바닥났을 때

| 상황 | 하는 일 |
|---|---|
| Claude 한도가 바닥남 | 구현은 Codex가 계속한다. Claude 리뷰가 필요한 PR은 초안으로 두고 머지하지 않는다 |
| Codex 한도가 바닥남 | 로직 티켓은 다음 날까지 기다린다. Claude 한도는 화면과 리뷰에 쓴다 |
| 둘 다 바닥남 | 시안을 그리거나, 문서를 쓰거나, 코드를 직접 읽는다 |
| 첫 주가 끝남 | 실제 사용량을 보고 이 문서의 배분을 다시 정한다 |

리뷰 없이 머지하는 길은 어떤 경우에도 열지 않는다.

## 2. 코드 작성 방식: tdd와 ponytail 함께 쓰기

테스트의 순서와 위치는 `tdd`(테스트를 먼저 쓰고 구현하는 스킬)가 정한다. 구현 코드의 양은 ponytail(코드를 가장 적게 쓰게 하는 작업 모드)이 정한다. 규칙 문장은 `AGENTS.md`에 있다.

| 결정 | 왜 |
|---|---|
| 동작이 바뀌는 티켓은 테스트할 경계(테스트가 코드를 부르는 지점) 목록을 먼저 정하고 사용자에게 확인받는다. 돈 계산, 판정, 권한, 개인정보, 동시성, 외부 실패(AI·푸시·로그인)를 따진다 | 모든 것을 테스트할 수는 없다. 그래서 틀리면 안 되는 곳에 테스트를 모은다 |
| 확인은 가능한 한 가장 높은 경계 하나에서 한다. 서버는 유스케이스·API, 앱은 화면 단위다. 낮은 경계의 테스트는 그곳에서만 드러나는 실패가 있을 때만 더한다 | 높은 경계의 테스트는 내부를 고쳐도 깨지지 않는다 |
| 테스트 하나를 쓰고 실패를 확인한 뒤, 통과할 만큼만 구현한다. 한 번 돌 때마다 결과를 한 줄씩 보고한다 | 테스트를 먼저 다 쓰면 실제 동작이 아니라 상상한 동작을 확인하게 된다 |
| ponytail은 구현 세션에서도 켜 둔다. 테스트 개수는 경계 목록이 정하고, ponytail이 줄이지 않는다. ponytail이 권하는 assert 자체 점검 대신 레포의 테스트 도구로 테스트를 쓴다 | 세션마다 끄고 켤 필요가 없다. 전역 CLAUDE.md의 "ponytail과 /tdd가 부딪치면 먼저 알린다"는 규칙은 이 레포에서 이 규칙으로 대신한다 |
| 정산 금액의 기대값은 [그룹 규칙 명세](../planning/rules-spec.md) 7-5절(검산한 정산 예시)에서 가져온다 | 코드와 같은 계산을 되풀이하는 테스트를 막는다 |

## 3. 설계 전략

| 결정 | 왜 |
|---|---|
| 용어의 원본은 루트 [용어집](../../GLOSSARY.md) 하나다. 용어가 정해지면 Claude가 문서 본문을 바로 고친다 | Claude와 Codex가 같은 말을 쓴다 |
| ADR은 `docs/adr/`에 둔다. 되돌리기 어렵고, 맥락 없이 보면 놀랍고, 실제 선택지 사이에서 고른 결정만 쓴다. | ADR이 쌓여도 읽을 가치가 남는다 |
| 서버는 Kotlin + Spring Boot 서버 하나다. 모듈은 identity, group, verification, judgment, ledger, notification 여섯 개다. 모듈 안은 헥사고날 구조(업무 규칙 코드를 DB·외부 서비스 코드와 떼어 두는 구조)로 짠다 | 모듈 이름이 그대로 PR 제목의 영역 이름과 구조 점검 묶음이 된다 |
| 레포 하나에 `backend/`, `app/`(Expo), `landing/`(Next.js), `contracts/`(API 계약)를 둔다 | 이슈, 규칙, 검사가 한 곳에 모인다 |
| 레포는 공개한다 | 포트폴리오에 레포 링크를 낸다. 공개 레포는 Actions가 무료다. 대신 이슈와 문서에 비밀값과 개인정보를 적지 않는다 |

## 4. 다크 팩토리

다크 팩토리는 이슈, PR, 정해진 시각을 신호로 받아 사람 손 없이 머지 직전까지 코드를 만드는 에이전트 묶음이다. 꼬박은 Claude Pro 요금제 한도 때문에 Actions에서 Claude를 돌리지 않는다. 지금은 자리마다 어떤 도구를 쓸지만 정해 두었고, 요금제를 올리면 작업을 하나씩 켠다.

| 자리 | 제품 | 지금 |
|---|---|---|
| 티켓 트래커 | GitHub Issues | 씀 |
| Git 호스트 | GitHub (`Jieunsse/kkobak`) | 씀 |
| 실행 관리자 | GitHub Actions | CI와 PR 검사만 |
| 러너 | Actions 러너 | CI와 PR 검사만. Claude Code Action은 켜지 않음 |
| 관측 도구 | Actions 실행 페이지 | 씀 |
| 티켓 소스 | 사람과 to-tickets | 씀 |

| 작업 | 지금 하는 곳 |
|---|---|
| 자동 리뷰 | Codex 클라우드 리뷰가 모든 PR을 본다. Codex가 만든 PR은 Claude가 로컬에서 두 축 리뷰를 한다 |
| 재작업 | 사람이 연 세션 |
| 분류 | 월요일 `/triage` |
| 구조 점검 | 운영 기간 금요일, 로컬 |
| 구현 | 로컬 Claude, 로컬 Codex |
| retro | 사람이 연 Claude 세션이 끝날 때 |

| 결정 | 왜 |
|---|---|
| Actions의 Claude 자동 리뷰는 설치하지 않는다 (2026-11-27). 처음에는 "자동 리뷰 하나만 켠다"로 정했다. 그 뒤에 정한 교차 리뷰가 같은 일을 하므로 바꿨다 | 켜 두면 같은 PR을 두 번 보고 Pro 한도만 쓴다 |
| Codex 리뷰 기준은 `AGENTS.md`의 "Review guidelines" 절에 둔다 | Codex 클라우드 리뷰가 이 절을 읽는다. Claude 두 축 리뷰의 기준 축도 같은 절을 본다 |

## 5. 브레이크

브레이크는 잘못된 코드가 머지되지 않게 막는 장치다.

| 결정 | 왜 |
|---|---|
| `main`에 보호 규칙을 건다. 직접 푸시를 막고 PR로만 머지한다. 필수 체크는 `backend`, `app`, `landing`(ci 워크플로), `pr-rules`다. squash 머지(PR의 커밋을 하나로 합쳐 넣는 방식)만 켠다 | CI가 실패한 PR이 머지되지 않는다 |
| 승인 필수는 켜지 않는다 | 혼자라 자기 PR을 승인할 수 없다 |
| CI의 세 작업은 폴더가 없으면 건너뛰고 성공으로 끝난다. `app/`과 `landing/`을 만들 때 `package.json`에 `lint`, `typecheck`, `test` 스크립트를 둔다 | 코드가 생기기 전에도 필수 체크가 대기 상태로 남지 않는다. CI가 이 세 스크립트 이름을 부른다 |
| backend는 빌드, 테스트, ktlint, detekt를 돌린다. app과 landing은 TypeScript strict, ESLint, 테스트를 돌린다. 예외 목록 없이 처음부터 실패시킨다 | 기존 위반이 없으니 기준선이 필요 없다 |
| 「리뷰 위치」 항목마다 「읽고 이해함」 체크박스를 두고, 모두 체크될 때까지 `pr-rules`가 실패한다. 에이전트는 이 체크박스를 체크하지 않는다 | 혼자일 때 "위험한 코드를 읽었다"는 기록을 남기는 유일한 장치다 |
| [리뷰 기준](../../CODING_STANDARDS.md)은 두 항목(금지하는 테스트 세 가지, 리뷰 위치 표시)으로 시작한다 | 리뷰어가 읽을 문서를 짧게 둔다 |
