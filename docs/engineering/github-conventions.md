# GitHub 규칙: 라벨·브랜치·제목·영역·양식·칸반

2026-11-27에 정했다. adflow(먼저 혼자 개발용 작업 흐름을 만든 다른 프로젝트)의 `docs/engineering/github-conventions.md`를 꼬박에 맞게 고쳤다. 일하는 흐름은 [작업 흐름](work-pipeline.md) 문서에 있다.

## adflow 규칙과 달라진 점

| 부분 | adflow | 꼬박 |
|---|---|---|
| 브랜치 | dev와 main | main 하나 |
| 구현 상태 라벨 | 팩토리 구현 / 구현 대기 | Codex 구현 / Claude 구현 |
| AI 리뷰 라벨 | AI 리뷰 통과·반려, 자동 수정 중단 | 없음. Actions에서 Claude 자동 리뷰를 돌리지 않는다 |
| 위치 라벨 | 웹·API·계약·인프라·문서 | 서버·앱·소개·계약·인프라·문서 |
| 칸반 이동 | `project-sync` 워크플로 | GitHub Projects의 기본 자동화 |

## 라벨

라벨 이름은 짧은 한글 명사다. 맷 포콕 스킬(Matt Pocock이 만든 Claude 작업 스킬 묶음)은 라벨을 영어 역할 이름으로 부른다. 이 역할 이름은 [docs/agents/triage-labels.md](../agents/triage-labels.md)의 대응표로 한글 라벨에 연결한다.

### 이슈 종류 (양식이 붙임)

| 라벨 | 맷 포콕 역할 | 뜻 |
|---|---|---|
| 버그 | `bug` | 동작이 구현 의도와 다르다 |
| 기능 | `enhancement` | 새 기능이나 개선 |

티켓은 종류 라벨이 없다. 기능 이슈의 하위 이슈라는 연결로 구분한다.

### 이슈 상태 (`/triage`, to-tickets가 붙임)

`/triage`는 이슈를 읽고 라벨을 붙여 분류하는 스킬이다. to-tickets는 스펙을 구현 단위의 티켓(하위 이슈)으로 나누는 스킬이다.

| 라벨 | 맷 포콕 역할 | 뜻 |
|---|---|---|
| 검토 대기 | `needs-triage` | 사람이 판단해야 한다. 월요일 `/triage`에서 본다 |
| 정보 필요 | `needs-info` | 더 알아봐야 시작할 수 있다 |
| Codex 구현 | `ready-for-agent` | 구현 설명(브리프)이 붙어 있다. 피그마나 사람이 직접 하는 테스트 없이 구현할 수 있다. Codex가 구현하고 Claude가 리뷰한다 |
| Claude 구현 | `ready-for-human` | 구현 설명(브리프)이 붙어 있다. 피그마 시안이나 사람의 판단이 필요하다. 사람이 연 Claude 세션이 구현하고 Codex가 리뷰한다 |
| 취소 | `wontfix` | 하지 않는다. 이유를 댓글로 남기고 닫는다 |

### 가설 검증 (스펙 이슈에만)

| 라벨 | 뜻 |
|---|---|
| 검증 대기 | 티켓이 모두 끝났고 사용자가 쓰는 중이다. 판정 시점을 기다린다 |
| 검증됨 | 판정 결과 가설이 맞았다 |
| 기각 | 판정 결과 가설이 틀렸다. 고치거나 지우는 이슈를 따로 연다 |

이슈 하나에는 종류 라벨 하나와 상태 라벨 하나만 붙는다. 구현을 시작하는 사람이 자기를 담당자로 지정한다.

### PR (본문 검사가 붙임)

| 라벨 | 뜻 |
|---|---|
| 중점 리뷰 | 「리뷰 위치」 칸에 항목이 있다. 머지 전에 그 코드를 연다 |
| 논의 필요 | 「결정 필요」 칸에 항목이 있다 |

### 위치 (`.github/labeler.yml`이 바뀐 파일 경로를 보고 자동으로 붙임)

| 라벨 | 경로 |
|---|---|
| 서버 | `backend/` |
| 앱 | `app/` |
| 소개 | `landing/` |
| 계약 | `contracts/` |
| 인프라 | `.github/`, `infra/` |
| 문서 | `docs/`, `*.md` |

계약 라벨이 붙은 PR은 서버와 앱이 둘 다 바뀐 계약에 맞는지 본다.

### 로드맵 (`/wayfinder`)

`/wayfinder`는 큰 작업을 지도(map) 이슈 하나와 하위 티켓으로 나눠 관리하는 스킬이다.

`wayfinder:map`, `wayfinder:research`, `wayfinder:prototype`, `wayfinder:grilling`, `wayfinder:task`를 영어 그대로 쓴다. [docs/agents/issue-tracker.md](../agents/issue-tracker.md)가 이 이름을 쓴다.

## 브랜치 이름

형식: `<종류>/<이슈 번호>-<영어 설명>`. 예: `feat/12-group-invite-link`

- `feat`·`fix`·`refactor`·`perf`·`test`는 이슈 번호가 꼭 있어야 한다. 코드 동작이 바뀌는 일은 티켓을 거쳐야 스펙 축 리뷰(PR을 스펙 이슈와 명세에 맞춰 보는 리뷰)가 볼 스펙이 생긴다.
- `docs`·`chore`·`ci`·`build`·`style`·`revert`는 이슈 번호 없이 `<종류>/<영어 설명>`으로 써도 된다.
- Codex에 구현을 맡길 때는 Codex 기본 브랜치 이름 대신 이 형식을 쓰라고 지시서에 적는다.

## 제목

### PR 제목 (squash 머지로 main에 남는 한 줄)

squash 머지는 PR의 커밋을 하나로 합쳐 넣는 방식이다. 그래서 main에는 PR 제목 한 줄만 남는다.

형식: `<종류>(<영역>): <한글 설명>`. 브랜치 안의 커밋 메시지는 검사하지 않는다.

| 종류 | 쓰는 때 |
|---|---|
| `feat` | 새 기능, 새 화면, 화면에 새 요소 |
| `fix` | 동작이 의도와 다른 것을 고침. 화면이 시안과 다른 것을 고침 |
| `refactor` | 동작이 그대로인 구조 변경 |
| `perf` | 성능 개선 |
| `test` | 테스트만 더하거나 고침 |
| `docs` | 문서만 고침 |
| `style` | 포매팅만 바꿈. 화면 모양이 바뀌면 `fix`나 `feat`을 쓴다 |
| `build` | 빌드 설정, 의존성 |
| `ci` | GitHub Actions, 검사 스크립트 |
| `chore` | 그 밖의 잡무 |
| `revert` | 되돌리기 |

### 이슈 제목

형식은 없다. 현상이나 결과를 명사형으로 30자 안쪽에 쓴다. 예: `마감 직전 인증이 결석으로 판정됨`

## 영역 (scope)

영역은 PR 제목의 괄호 안에 쓰는 이름이다. 서버와 앱이 같은 이름을 쓴다. 목록 밖 이름을 쓰면 `pr-rules`가 막는다.

| 영역 | 범위 |
|---|---|
| `identity` | 카카오·애플 로그인, 회원 |
| `group` | 그룹, 멤버, 규칙, 초대, 규칙 카드 |
| `verification` | 인증 사진, AI 확인, 그룹원 확인, 이의 제기 |
| `judgment` | 인증일 계산, 마감 판정, 쉬는 날, 복귀 |
| `ledger` | 장부, 벌금 모음, 정산표, 탈퇴 정산 |
| `notification` | 푸시 알림 |
| `app` | 앱 공용 부품, 내비게이션, 디자인 토큰, 인증 카드 공유 |
| `landing` | 소개 페이지 |
| `contracts` | 여러 영역에 걸친 API 계약 변경 |
| `infra` | 배포, 서버 설정, GitHub Actions, 검사 스크립트 |
| `docs` | 기획·설계 문서 |

서버와 앱은 영역이 아니라 위치 라벨로 구분한다. 그래서 같은 기능의 서버 변경과 앱 변경이 같은 영역으로 묶인다.

## 이슈 양식

양식 파일은 `.github/ISSUE_TEMPLATE/`의 `feature.yml`, `bug.yml`, `ticket.yml`이다. `config.yml`이 양식 없는 빈 이슈를 막는다.

| 양식 | 붙는 라벨 | 칸 (굵게 = 필수) |
|---|---|---|
| 기능 | 기능 | **현재 문제**, **목표**, **완료 조건**, 제외 범위, **영역**, 관련 정책(`docs/planning/` 문서와 절 번호), 피그마 링크 |
| 버그 | 버그 | **재현 순서**, **구현 의도**, **실제 결과**, **위치**, 로그·스크린샷, **우선순위** |
| 티켓 | (없음) | **상위 이슈**, **작업 내용**, **테스트 항목**, 피그마 프레임, 선행 이슈(GitHub 연결로 표시) |

티켓의 「테스트 항목」은 그대로 테스트 이름이 된다. 이 이름은 PR의 「테스트 항목」 칸에 다시 나온다.

## PR 양식

칸: **요약**, **결정 필요**, **테스트 항목**, **리뷰 위치**, **롤백**, **검증**, 스크린샷(앱·소개 화면이 바뀔 때), 상세(접음), `Closes #번호`.

- 요약은 두 문장으로 쓴다. 첫 문장은 무엇이 바뀌는지, 둘째 문장은 그래서 사용자(그룹장·멤버)에게 무엇이 달라지는지 쓴다.
- 테스트 항목은 바뀐 테스트의 이름을 그대로 옮긴다.
- 리뷰 위치는 최대 3곳까지 적고, 곳마다 이유 한 줄과 「읽고 이해함」 체크박스를 둔다. 돈 계산, 판정, 권한, 개인정보가 바뀌는 곳을 적는다. 위험이 낮으면 「없음」이라고 쓴다.
- 롤백 칸에는 「쉬움」 또는 「어려움」과 그 이유를 쓴다.
- 맷 포콕 `pr` 스킬(PR 본문을 쓰는 스킬)이 요구하는 세 요소는 우리 양식의 칸에 나눠 넣는다. 변경 그림은 상세, 전후 증거는 검증·스크린샷, 머지 위험은 롤백·리뷰 위치 칸이다.

### 본문 검사 (`pr-rules`)

`.github/scripts/pr-rules.mjs`가 제목, 브랜치, 본문을 본다.

- 제목이 종류·영역 형식을 따르는지
- 브랜치 이름이 위 형식인지
- 칸 제목이 모두 있는지, 요약이 두 문장 이하인지, 리뷰 위치가 3곳 이하인지
- 금지어: 짚다, 끌어내다, 해당, 진행하다, 수행하다, ~를 통해, ~에 대해, 기반으로. retro(작업을 마친 뒤 실수를 돌아보는 회고)에서 새 금지어를 찾을 때마다 더한다
- 「리뷰 위치」의 「읽고 이해함」이 모두 체크됐는지. 본문을 고치면 검사가 다시 돈다
- `app/`이나 `landing/`이 바뀌었는데 스크린샷 칸이 비었는지
- 「중점 리뷰」·「논의 필요」 라벨을 붙이거나 뗀다

## 칸반 (GitHub Projects)

개인 계정에 공개 프로젝트를 하나 만들고 꼬박 이슈를 모두 올린다. PR은 올리지 않는다.

| 칸 | 옮기는 것 |
|---|---|
| 백로그 | 이슈가 열리면 자동으로 들어온다 (기본 자동화) |
| 이번 주 | 월요일에 이번 주 할 이슈를 옮긴다 |
| 진행 | 구현을 시작할 때 옮긴다 |
| 완료 | 이슈가 닫히면 자동으로 옮겨진다 (기본 자동화) |

혼자라서 라벨을 보고 칸을 옮기는 워크플로는 두지 않는다. 칸을 손으로 옮기는 일이 하루 몇 번을 넘어 귀찮아지면 그때 넣는다.

## 적용 순서

1. 라벨을 만들고 GitHub 기본 라벨 9개를 지운다.
2. 이슈 양식, PR 양식, `labeler.yml`, `pr-rules`를 넣는다.
3. 레포 설정에서 squash 머지만 켜고, `main` 보호 규칙에 필수 체크를 지정한다.
4. `gh auth refresh -s project`로 권한을 더한 뒤 프로젝트를 만든다.
